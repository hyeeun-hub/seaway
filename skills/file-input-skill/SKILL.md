# file-input-skill

## 목적
ERP 엑셀 파일 업로드가 들어오면 가장 먼저 접수한다.  
파일을 저장/정리하고, 업로드 시점을 기록하며, 파일 기본 구조를 확인해 이후 분석/검증이 바로 쓸 수 있는 파일 참조 정보를 남긴다.  
내용 해석은 하지 않고, “분석 가능한 상태로 넘긴 파일 정보”까지 만드는 것이 역할이다.

## 언제 실행하나
- ERP 엑셀 파일이 업로드되면 가장 먼저 실행한다.
- 파일이 1개든 여러 개든 접수 단위별로 처리한다.
- 수동 보정 없이 업로드된 파일 자체를 기준으로 접수한다.

## 입력
- 업로드 파일(엑셀, .xls/.xlsx 중심)
- 파일명
- 업로드 시점
- 파일 기본 메타정보(확장자, 시트 수, 제목행 유무, 행 수, 열 수 등)

## 처리
- 업로드된 파일을 저장/정리하고, 이후 단계가 참조할 수 있는 파일 식별 정보를 만든다.
- 업로드 시점을 기록한다.
- 파일 기본 메타정보를 정리한다.
- 시트 수, 행 수, 열 수, 제목행/헤더행/데이터행 존재 여부 같은 기본 구조를 확인한다.
- 중복 접수 의심 여부를 확인한다.
  - 파일명, 업로드 시점, 파일 내용 구조를 함께 본다.
  - 짧은 간격 안에 같은 파일이 다시 들어오면 중복 의심으로 남긴다.
- 파일이 비어 있거나, 읽을 수 없거나, 기본 구조가 확인되지 않으면 접수 단계에서 이상 항목으로 남긴다.
- 내용 파싱/해석은 하지 않는다. 내용 처리는 analyze-skill이 담당한다.

## 출력
- 저장 위치
- 처리 상태
- 중복 여부
- 업로드 시점
- 분석용 파일 참조 정보
  - 파일 식별 정보
  - 대상 시트
  - 기본 구조 정보
  - 이후 단계에서 참고할 파일 메타데이터
- 이상 접수 시 이상 항목
  - 파일 상태
  - 이상 유형
  - 원인 힌트

## 산출물
- 파일 접수 기록
- 분석/검증이 참조할 파일 참조 정보
- 중복 또는 이상 접수 시 상태 정보

## 실행 조건
- 업로드된 파일과 업로드 시점이 있어야 실행한다.
- 파일 참조 정보는 이후 스킬/에이전트가 바로 사용할 수 있게 정리한다.
- 사람의 수동 파일 수정이나 보정 없이 접수 완료까지 이어져야 한다.

## 결과 전달 방식
- 이 스킬의 결과는 다음 단계로 자동으로 넘겨진다.
- 사용자는 중간 접수 결과를 따로 보지 않고, 최종 결과에서 확인할 수 있게 한다.
- 접수 단계에서 이상이 있으면 그 사실도 이후 검증/검수 쪽으로 넘길 수 있게 남긴다.

## 재사용성
- 특정 한 파일만 처리하는 스킬이 아니라, ERP 엑셀 파일을 접수하는 공통 처리로 쓸 수 있게 만든다.
- 제목행 위치나 헤더 구성이 조금 달라도 접수·정리·메타 정리 흐름을 다시 쓸 수 있게 한다.
- 실제 열 해석은 analyze-skill이 담당하므로, 이 스킬은 접수/정리/참조 정보 생성에 집중한다.

## 비고
- 이 스킬은 파일을 예쁘게 읽는 역할보다, “접수해서 정리된 상태로 다음 단계에 넘기는” 역할이다.
- 파일 내용 해석은 analyze-skill, 이상 점검은 verify-skill이 담당한다.

## 범위

### 처리하는 것
- `.xls`(BIFF) / `.xlsx` ERP 엑셀 파일. `state-schema.md` §3 매핑표에 등록된 4종
- 시트 수, 행 수, 열 수, 제목행/헤더행/데이터행 위치 확인
- 파일 해시 계산 및 파일 처리 기록 기록/조회(`ProcessedFile` 테이블, `state-schema.md` §7)
- 파일 단위 중복 접수 판정(1차 방어선)

### 처리하지 않는 것
- **셀 값 해석, 날짜/금액 정규화, 프로젝트 매칭** → analyze-skill
- **거래 단위 중복 판정** → analyze-skill(2차 방어선)
- **파일 수정, 값 보정, 열 추측 보완** → 하지 않는다. 매핑표에 없는 열 구성이면 `status: "rejected"`로 남기고 verify로 넘긴다
- CSV, PDF, 이미지, 한글 문서

### 제약
- 파일 내용을 메모리에 전부 올리지 않는다. 구조 확인에 필요한 범위만 읽는다
- 원본 파일을 수정하지 않는다. `data/`는 읽기 전용으로 다룬다

## 예시

### 입력

```
업로드: 4개 파일
  매출_세금계산서_2026년1-5월.xls
  매입(세금계산서)_2026년1-5월.xls
  매입(간이영수증)_202608031250.xls
  매입(국세_지방세)_202608031254.xls
업로드 시점: 2026-08-06T14:20:03+09:00
```

### 출력

| 파일 | kind | 시트 | 헤더행 | 데이터 시작 | 데이터행 | 상태 |
|---|---|---|---|---|---|---|
| 매출_세금계산서_2026년1-5월.xls | `매출-세금계산서` | sheet1 | 1 | 2 | 11 | processed |
| 매입(세금계산서)_2026년1-5월.xls | `매입-세금계산서` | `sheet1 -1` | 1 | 2 | 141 | processed |
| 매입(간이영수증)_202608031250.xls | `매입-간이영수증` | sheet1 | 1 | 2 | 712 | processed |
| 매입(국세_지방세)_202608031254.xls | `매입-국세지방세` | sheet1 | 1 | 2 | 5 | processed |

```
합계 869행 / 중복 접수 0건 / 접수 이상 0건
ProcessedFile: 4건 신규 기록
```

진행 표시(`SPEC.md` §3): `파일 접수 완료 — 4개 파일, 869행`

### 같은 파일을 다시 업로드한 경우

```
매출_세금계산서_2026년1-5월.xls
  → file_hash 일치. status: "skipped_duplicate", 파싱하지 않음
진행 표시: 파일 접수 완료 — 4개 파일 중 1개 중복 스킵, 858행
```

---

## 성공 기준

- [ ] 4개 파일 모두 `kind`가 매핑되고 `status: "processed"`로 기록된다
- [ ] 데이터행 수가 11 / 141 / 712 / 5로 집계된다
- [ ] `매입(세금계산서)` 파일의 시트명이 `sheet1 -1`(뒤에 공백과 -1이 붙은 형태)임에도 정상 접수된다
- [ ] 모든 파일에 `file_hash`가 기록된다
- [ ] 같은 파일을 두 번째로 업로드하면 파싱하지 않고 `skipped_duplicate`로 처리된다
- [ ] 셀 값 해석 결과(금액 합계, 프로젝트명 등)가 이 단계 출력에 없다
- [ ] 원본 파일이 수정되지 않았다
