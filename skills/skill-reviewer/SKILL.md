# SKILL.md 품질 리뷰어

## 개요
이 스킬은 사용자가 입력한 SKILL.md 파일이 Timely 스킬 품질 기준 5가지를 만족하는지 평가하고, 조건별 통과/실패·진단 원인·구체적 개선안이 담긴 `.md` 리포트 파일을 생성합니다.

## 언제 사용
- 새로 작성한 SKILL.md의 품질을 셀프체크하고 싶을 때
- 팀원에게 공유하기 전 스킬의 품질을 검증하고 싶을 때
- 기존 스킬을 리팩토링하기 전 현재 상태를 진단하고 싶을 때

## 5가지 평가 조건

평가 항목은 다음 5가지입니다. 각 조건은 **통과(Pass)** 또는 **실패(Fail)** 로 판정됩니다.

| # | 조건 | 설명 |
|---|------|------|
| 1 | **단일 기능** | 하나의 스킬이 담당하는 기능이 명확히 하나여야 함. 여러 책임이 섞여 있으면 실패 |
| 2 | **명확한 설명** | description 및 본문에서 *무엇을* 하는지 모호함 없이 서술되어야 함 |
| 3 | **범위 명시** | 처리할 수 있는 입력과 처리할 수 없는 입력이 경계와 함께 명시되어 있어야 함 |
| 4 | **예시 포함** | 최소 하나 이상의 사용 예시(입력·출력 쌍)가 본문에 포함되어야 함 |
| 5 | **확인 가능** | 평가자가 리포트 생성 결과를 열어 내용을 직접 검증할 수 있어야 함 (예: 파일이 실제로 생성됨) |

> 💡 5가지 조건은 이 스킬 자체의 SKILL.md에도 동일하게 적용됩니다.

## 사용 방법

### 1. 리뷰할 SKILL.md 제공

리뷰를 원하는 SKILL.md 파일의 경로를 알려주거나, 파일 내용을 직접 붙여넣으세요.

```
./SKILL.md 를 리뷰해줘
```

### 2. 리포트 생성

이 스킬은 다음 구조로 리포트를 작성합니다.

- **리포트 파일명**: `skill-<skill-name>-review-<YYYYMMDD>.md` (규칙: 소문자 스킬명, 하이픈 연결, 오늘 날짜 YYYYMMDD)
- **리포트 구조**:
  1. **요약** — 총점(5점 만점), 통과/실패 개수, 한 줄 결론
  2. **조건별 평가 표** — 조건명 · 결과 · 진단 원인 · 개선안
  3. **종합 의견** — 전체 품질에 대한 코멘트와 우선순위 높은 개선 항목 3개

### 3. 결과 확인

생성된 리포트 파일을 열어 확인합니다.

```
열어줘: skill-erp-dashboard-review-20260804.md
```

## 예시

### 입력

```
./SKILL.md 를 리뷰해줘
```

**SKILL.md 내용 (전체):**

```md
---
name: greeting
description: 인사
---

# 인사 스킬

인사를 해줍니다.
```

### 출력 (리포트 파일 본문):

````md
# 분석 리포트 — greeting

## 분석 대상

- 대상 SKILL.md: greeting
- 평가일: 2026-08-04

## 평가 결과

| 조건 | 통과/실패 | 원인 | 개선안 |
|---|---|---|---|
| 단일 기능 | 통과 | "인사"라는 단일 기능만 담당 — 불분명하게 섞이지 않음 | — |
| 명확한 설명 | 실패 | description이 "인사" 두 글자뿐. 무엇을 어떻게 하는지 알 수 없음 | "사용자 이름 또는 상황에 맞는 한국어/영어 인사말을 생성한다" 등으로 구체화 |
| 범위 명시 | 실패 | 입력(어떤 형식의 입력을 받는지)·출력(어떤 인사말을 생성하는지) 경계가 없음 | "입력: 사용자 이름(선택) + 언어(ko/en), 출력: 1~3줄 인사말" 등으로 명시 |
| 예시 포함 | 실패 | 사용 예시가 전혀 없음 | 아래 예시 블록 추가: `## 예시` → `입력: 이름=철수, 언어=ko` → `출력: 안녕 철수!` |
| 확인 가능 | 통과 | 이 스킬을 실행하면 인사말이 출력되므로 확인 가능 | — |

## 종합 결과

- 통과 항목 수: 2/5
- 종합 판단: [❌] 개선 후 재평가 필요

## 한 줄 총평

description이 "인사" 두 글자뿐이고 범위·예시가 전혀 없어 스킬의 실체를 파악할 수 없습니다. description을 한 문장으로 채우고 입력/출력 형식과 예시만 추가해도 5점 만점에 4점 이상 도달할 수 있습니다.

### 우선순위 높은 개선 항목 (Top 3)

1. **[명확한 설명]** — description을 "사용자 이름 또는 상황에 맞는 한국어/영어 인사말을 생성한다" 등 구체적인 한 문장으로 고치세요.
2. **[범위 명시]** — 입력(사용자 이름, 언어)과 출력(1~3줄 인사말) 형식을 명시하세요.
3. **[예시 포함]** — 최소 1개의 입력-출력 예시를 추가하세요.
````

## 리포트 템플릿 (내부 구조)

리포트 생성 시 사용하는 내부 체크리스트는 다음과 같습니다.

```yaml
evaluation:
  - condition: 단일 기능
    check: |
      description과 본문이 하나의 책임만 다루는가?
      - description에 "~하거나", "또는", "및" 등으로 여러 작업이 연결되어 있지 않은가?
      - 목적이 한 문장으로 정리되는가?
  - condition: 명확한 설명
    check: |
      description이 동사+대상을 포함한 완결 문장인가?
      - description이 "~한다", "~생성한다", "~평가한다" 등 동작이 명확한 종결어미로 끝나는가?
      - description만 읽고도 "무엇을 / 언제 / 어떤 형식으로" 만드는지 즉시 파악되는가?
  - condition: 범위 명시
    check: |
      입력 타입/값, 처리 안 하는 것(non-scope)이 기술되어 있는가?
      - "포함" 또는 "## 범위" 섹션에 처리하는 입력이 명시되어 있는가?
      - "제외" 또는 "처리하지 않는 것"이 명시되어 있는가?
      - 제약(시간, 분량, 보안 등)이 있다면 함께 기술되어 있는가?
  - condition: 예시 포함
    check: |
      템플릿 섹션이 있고 실제 출력물 예시가 1개 이상 있는가?
      - ## 템플릿 또는 ## 예시 섹션이 존재하는가?
      - 예시에 더미 데이터(XXX, 샘플명 등)가 포함된 실제 출력물 형태가 보이는가?
      - 입력-출력 쌍이 최소 1개 이상 제시되어 있는가?
  - condition: 확인 가능
    check: |
      성공 기준이 "예/아니오"로 즉시 판단 가능한 형태로 본문에 있는가?
      - 성공 기준이 [ ] 체크박스 형태로 작성되어 있는가?
      - 체크리스트 항목이 3개 이상 있는가?
      - 각 항목이 "예/아니오"로 답할 수 있는 구체적인 문장인가?
```

## 파일명 규칙

- **리포트 파일명**: `skill-<skill-name>-review-<YYYYMMDD>.md`
- **규칙**:
  - 스킬명은 lowercase, 하이픈(-)으로 연결 (예: `erp-dashboard`)
  - 날짜는 오늘 날짜 YYYYMMDD 형식 (예: 20260804)
  - 확장자는 .md
- **검증**: 생성 후 파일명이 규칙에 맞는지 확인하고, 틀리면 수정합니다.
  - 예: `SKILL.md` → `skill-skill-review-20260804.md` (O)
  - 예: `review-20260804.md` → 스킬명이 누락되어 수정 필요 (X)

## 팁

- 새로 만든 스킬은 **항상 이 스킬로 셀프 리뷰**한 뒤 커밋하는 습관을 들이면 품질이 크게 올라갑니다.
- `description`이 짧을수록 2번 조건에서 실패하기 쉽습니다 — 한 문장 이상으로 풀어쓰세요.
- 예시 하나만 추가해도 4번 조건을 즉시 통과할 수 있습니다.
- 파일명 규칙을 지키지 않으면 추후 관리가 어려우니 리포트 생성 시 반드시 확인하세요.
