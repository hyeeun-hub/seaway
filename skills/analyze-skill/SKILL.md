# analyze-skill

## 목적
접수된 ERP 엑셀 파일을 실제로 거래 데이터로 바꾸고, 프로젝트/현장 단위로 손익을 계산하며, 월별로 집계하고, 일반관리비성 항목을 분류한다.  
이후 검수/분류, 결과 생성/조회, 캘린더/챗봇/요약, 자동 검사/검증이 바로 쓸 수 있는 분석 결과를 남긴다.

## 언제 실행하나
- file-input-skill이 파일 접수/정리/참조 정보 생성을 마친 뒤 실행한다.
- 업로드 파일 또는 파일 참조 정보가 준비되면 실행한다.
- 여러 파일(매입/매출/간이영수증/세금 등)이 함께 들어와도 같은 흐름으로 처리할 수 있게 한다.

## 입력
- 업로드 파일 또는 파일 참조 정보
- 프로젝트 목록/매칭 규칙
- 분석 설정/규칙(용도→계정 분류, 일반관리비 분류 기준, 손익 계산 기준 등)
- 업로드 시점
- 필요 시 기준 월/조회 조건(분석 결과에서 월별/기간별 범위를 구분하는 데 사용)

## 처리
- 각 파일의 시트·제목행·헤더행·데이터행을 확인하고 거래 단위로 정규화한다.
- 파일별 공통 핵심 항목을 기준으로 한 거래 레코드 형태로 맞춘다.
  - 거래일자
  - 금액
  - 용도/계정 성격
  - 내용
  - 프로젝트/현장
  - 증빙/참조 정보
  - 기타 참고 열
- 날짜 형식, 금액 형식, 공백/결측 처리를 정리한다.
- 프로젝트/현장 매칭을 수행한다.
  - 프로젝트/현장 값이 있으면 그 기준으로 매칭
  - 값이 없거나 애매하면 미매칭 또는 신규 프로젝트 후보로 남김
- 손익을 계산한다.
  - 매출 해당 거래와 매입/경비 해당 거래를 구분해 프로젝트별 손익을 계산
  - 필요 시 계정/용도 성격에 따라 수익·비용 성격을 구분
- 월별로 집계한다.
  - 거래일자 기준으로 월을 나누어 월별 손익/현황을 정리
  - 특정 월만 먼저 들어오면 그 월 범위만 반영하고, 이후 같은 월 데이터가 추가되면 중복 제외 후 재생성할 수 있게 정리
- 일반관리비성 분류 결과를 만든다.
  - 사무실운영, 세금/공과금, 수수료, 소모성 비용 등 일반관리비로 볼 수 있는 항목을 분류
  - 분류가 애매한 항목은 분류 보류/확인 필요로 남김

## 중복 제외 원칙
- 같은 거래로 볼 수 있는 항목이 모두 같으면 중복으로 보고 반영하지 않는다.
- 중복 판단에는 다음 같은 핵심 항목을 사용한다.
  - 거래일자
  - 금액
  - 프로젝트/현장
  - 내용/용도
  - 필요 시 증빙/참조 정보
- 월별로 데이터가 추가 유입되는 경우에도 같은 원칙으로 중복을 제외하고 나머지를 반영한다.

## 출력
- 프로젝트별 손익
- 월별 손익
- 일반관리비 분류 결과
- 분석 시점
- 기준 파일 정보
- 매칭 결과
- 신규 프로젝트 후보
- 정규화 거래 데이터(참고용)
- 분석 중 발생한 이상/주의 항목
  - 형식 이상
  - 미매칭 과다
  - 분류 불가/보류 과다
  - 월별 집계 불일치 의심
  - 중복 제외/재생성 관련 주의 사항

## 산출물
- 프로젝트별 손익 데이터
- 월별 손익 데이터
- 일반관리비 분류 결과
- 프로젝트 매칭 결과 및 신규 프로젝트 후보
- 분석 기준 시점 및 기준 파일 정보

## 실행 조건
- 분석할 파일 또는 파일 참조 정보가 있어야 한다.
- 프로젝트 목록/규칙, 분석 설정/규칙이 있으면 더 정확하게 처리한다.
- 규칙만으로 확정하기 어려운 거래는 강제로 결론을 만들지 말고, 검수/분류 단계에서 다룰 수 있게 남긴다.

## 결과 전달 방식
- 이 스킬의 결과는 다음 단계로 자동으로 넘겨진다.
- 사용자는 중간 분석 결과를 따로 보지 않고, 최종 결과에서 확인할 수 있게 한다.
- 분석 중 이상/주의 항목이 있으면 이후 검증/검수 쪽으로 넘길 수 있게 남긴다.

## 재사용성
- 특정 1개 파일만 처리하는 스킬이 아니라, 여러 ERP 엑셀 파일을 같은 방식으로 파싱·정규화·집계할 수 있게 만든다.
- 파일별 열 차이는 접수/파싱 단계에서 흡수하고, 분석 단계는 공통된 거래 레코드 구조를 기준으로 동작하게 한다.
- 프로젝트 매칭 규칙, 분류 규칙을 바꾸면 같은 구조로 다시 쓸 수 있게 한다.

## 비고
- 이 스킬은 “정답 회계 분개”를 강제하는 단계가 아니라, 이후 검수/분류와 검증이 다룰 수 있는 분석 결과를 실제로 만드는 단계다.
- 분류가 애매하거나 매칭이 불확실한 항목은 결과를 비워두기보다 확인 필요로 남겨서 검수/분류로 넘긴다.

## 범위

### 처리하는 것
- `state-schema.md` §3 매핑표에 따른 열 해석과 §5 정규화
- `(tx_key, seq)` 산출 및 거래 단위 중복 판정(2차 방어선)
- 거래/파일 처리 기록 갱신(`Transaction`/`ProcessedFile` 테이블, `state-schema.md` §7·§8)
- 프로젝트/현장 매칭, 프로젝트별 손익, 월별 집계, 일반관리비 후보 분류
- `비고` 열에서 `settle_date` / `settle_method` 파싱

### 처리하지 않는 것
- **확인 필요 거래의 분리, 문제 유형 판정, 확정/제외/수정 결정** → classify-skill
- **조회 필터, 리포트 생성, 전월 대비 증감** → query-export-skill
- **회수 캘린더 구성, 확정/예정 판정** → calendar-chatbot-skill. 이 스킬은 `settle_date` 파싱까지만 한다
- **빈 값 추론 보완.** `proj`가 비어 있으면 비운 채로 넘긴다. 인명으로 보이는 `proj`도 그대로 둔다
- **정답 회계 분개.** 규칙으로 확정되지 않는 계정 판단은 하지 않는다

### 왜 한 스킬인가
파싱·정규화·매칭·집계는 **거래 데이터를 한 번 훑는 동일 패스**에서 수행되며 중간 산출물이 서로에게만 쓰인다.
분리하면 정규화 결과를 스킬 경계로 직렬화해 주고받아야 해서, 단일 책임이 아니라 결합만 늘어난다.
판단이 필요한 지점(무엇이 문제인가)은 classify로 완전히 분리돼 있다.

### 제약
- 원본 거래를 수정하지 않는다. `Transaction` 테이블은 append-only
- 규칙만으로 확정할 수 없으면 결론을 만들지 않고 `use`/`proj`를 원문 그대로 남긴다

## 예시

### 입력 (원본 시트 1행)

```
파일: 매출_세금계산서_2026년1-5월.xls, 행 2
작성일자=2026-05-29  공급받는자상호=(주)성일건설  증빙=세계
합계금액=42350000  용도=매출  내용=한림,애월,성산 방충재교체 외
프로젝트/현장=2025 항만시설 유지보수공사  비고=2026-06-11 계좌
```

### 출력 (정규화 거래 레코드)

```json
{
  "tx_key": "sha256:8c21…", "seq": 1,
  "kind": "매출-세금계산서", "side": "매출",
  "date": "2026-05-29", "month": "2026-05",
  "place": "(주)성일건설", "amount": 42350000,
  "proj": "2025 항만시설 유지보수공사",
  "use": "매출", "content": "한림,애월,성산 방충재교체 외",
  "evidence": "세계", "payer": null,
  "settle_date": "2026-06-11", "settle_method": "계좌",
  "source_file": "매출_세금계산서_2026년1-5월.xls", "source_row": 2
}
```

### 출력 (월별 손익 — 869건 전량 기준)

| 월 | 매출 | 매입 | 손익 |
|---|---:|---:|---:|
| 2026-01 | 143,000,000 | 109,803,643 | 33,196,357 |
| 2026-02 | 0 | 92,578,174 | -92,578,174 |
| 2026-03 | 143,330,000 | 68,278,391 | 75,051,609 |
| 2026-04 | 59,950,106 | 99,681,402 | -39,731,296 |
| 2026-05 | 206,900,000 | 122,835,569 | 84,064,431 |

2026-02는 매출이 0이다. **데이터 누락이 아니라 그 달에 세금계산서 발행이 없었던 것**이므로,
집계에서 월을 빼지 않고 매출 0으로 남긴다. 사유는 이상 항목이 아니라 기준 정보로 넘긴다.

### 출력 (프로젝트별 손익 — 상위)

| 프로젝트/현장 | 매출 | 매입 | 손익 |
|---|---:|---:|---:|
| 추자 예초 해상부유구조물 | 289,047,720 | 200,413,268 | 88,634,452 |
| 2026도두항부잔교설치공사 | 117,330,000 | 115,340,498 | 1,989,502 |
| 2026 여수 신북항 해경선 접안시설 | 68,800,000 | 12,626,390 | 56,173,610 |
| 2025 항만시설 유지보수공사 | 42,350,000 | 24,781,170 | 17,568,830 |
| 창조이엔지 | 21,489,886 | 21,489,886 | 0 |
| 2025년 추자면 대서리 부잔교 | 0 | 77,512,024 | -77,512,024 |

### 출력 (일반관리비 후보 / 미매칭)

| 구분 | `proj` 값 | 금액 | 판정 |
|---|---|---:|---|
| 일반관리비 후보 | 사무실운영 | 12,636,411 | 프로젝트 아님. 일반관리비로 분류 |
| 일반관리비 후보 | 연구전담부서 | 4,680,400 | 프로젝트 아님. 일반관리비로 분류 |
| 일반관리비 후보 | 공장운영 / 공장전기 / 숙소전기 | 3,185,030 | 프로젝트 아님. 일반관리비로 분류 |
| 미매칭 후보 | 차내윤 | 164,520 | 인명으로 보임. 확정하지 않고 classify로 넘김 |
| 미매칭 후보 | 송인석 | 1,597,194 | 인명으로 보임. 확정하지 않고 classify로 넘김 |
| 미기재 | (공백) | 4,664,910 | `proj` 공백. classify로 넘김 |

### 출력 (누적 보관 결과)

```
tx_added: 869   tx_skipped_duplicate: 0   tx_total: 869
processed_files: 4건 갱신
```

진행 표시: `분석 완료 — 신규 거래 869건 추가, 중복 0건 스킵`

## 성공 기준

- [ ] 869건 전량이 `Transaction` 테이블에 누적되고, `tx_added + tx_skipped_duplicate = 869`이 성립한다
- [ ] 2026-02-12 아시아나항공 85,400원 3건이 `seq` 1/2/3으로 모두 남는다(합계 256,200원)
- [ ] 2026-04-08 `창조이엔지` 21,489,886원이 매출/매입 2건으로 남고, 손익이 0으로 계산된다
- [ ] 2026-01 원천세 금액 공백 1건이 `amount: null`로 남고 0으로 채워지지 않는다
- [ ] 2026-02 매출이 0으로 집계되고, 월이 표에서 삭제되지 않는다
- [ ] 프로젝트별 손익 합계가 월별 손익 합계와 일치한다
- [ ] `차내윤`/`송인석`이 프로젝트로 확정되지 않고 미매칭 후보로 남는다
- [ ] 매출 11건 전부에 `settle_date`가 채워진다
- [ ] 같은 파일을 재업로드하면 `tx_added: 0`, `tx_total`이 증가하지 않는다
